# SDKKorovinPortfolio — журнал оптимизации

Ход и результаты поэтапной оптимизации робота. План этапов описан в
[`SDKKorovinPortfolio.md`](SDKKorovinPortfolio.md), раздел «План оптимизации».
Прогоны выполняются через MCP API OsEngine (`optimizer_*`).

## Условия эксперимента

| | |
|---|---|
| Робот | `SDKKorovinPortfolio` |
| Сет данных | `MoexSecurities`, свечи, 42 бумаги |
| Полный диапазон данных | 04.01.2016 — 20.08.2026 |

| Потоков оптимизации | 8 |

### Зафиксированные параметры робота

Одинаковы во всех прогонах, в оптимизацию не включаются:

| Параметр | Значение | Почему |
|---|---|---|
| `Regime` | `On` | рабочий режим |
| `Reopen mode` | `On` | обязателен в тестере: иначе выручка от частичных продаж не возвращается в портфель |
| `Ladder mode` | `Continuous` | оптимизируется непрерывная модель загрузки |
| `Warmup policy` | `UseAvailable` | см. «Прогрев в проверочном периоде» |
| `Warmup min days` | 120 | |

### Прогрев в проверочном периоде

Фаза `OutOfSample` в OsEngine — **отдельный прогон**, робот в ней стартует с нуля.
При `Warmup policy` = `NoTrade` или `BaseWeightsOnly` лестница включилась бы только через
`Long sma period` (200) торговых дней, то есть съела бы почти весь 2025 год.

Поэтому во всех прогонах стоит `UseAvailable` с `Warmup min days` = 120: лестница включается
примерно через полгода после старта фазы. Условие одинаково для всех кандидатов, поэтому
сравнение честное, но помнить об этом стоит: первые ~6 месяцев проверочного периода робот
работает по базовым весам.

### Критерий отбора

Основной — **`total_profit` на фазе `OutOfSample`**, как и заказано.

Вспомогательные: `positions_count` (оборот), `profit_factor`, поведение в InSample
(кандидат, хороший только на проверке, но провальный на обучении, — случайность).

**Внимание:** поле `max_draw_down` из отчёта оптимизатора считается функцией
`GetMaxDownPercent` по массиву позиций и в наших прогонах даёт неинтерпретируемые значения
(например −616 % на InSample). Как просадку депозита его читать нельзя. Для контроля просадки
нужен отдельный прогон в тестере с чтением `bot_journal_get_drawdown`.

6,08–6,93 млн, то есть аллокация за девять лет решает мало, а за полтора года — почти всё.

**Аллокация не оптимизируется, она задаётся.** Дальнейшие этапы прогоняются на выбранной
волевым решением аллокации.

## Как задавать параметры оптимизатору — важная особенность

Обнаружено по ходу работы и стоило переигровки половины этапов.

`optimizer_params_set` принимает поля `value`, `start`, `stop`, `step`, `on`. Так вот:

* **строковые** параметры (`Regime`, `Reopen mode`, `Warmup policy`, `Ladder mode`) применяются
  через `value` и при `on: false` — работают как ожидается;
* **числовые** параметры при `on: false` в прогон идут **со своим `default_value`**, а не с
  заданным `value`. При этом `optimizer_params_get` показывает заданное значение — то есть
  расхождение никак не видно, пока не посмотришь параметры внутри отчёта о прогоне.

Проверка, вскрывшая это: контрольный прогон показал в отчёте `Band abs percent` = 1,5 (дефолт),
хотя перед запуском было выставлено 4 и `params_get` это подтверждал.

**Правило: числовой параметр фиксируется только через `on: true` со `start = stop = значение`.**
Число прогонов при этом не растёт — перебор из одного значения.

### Последствие для методики

Первая волна этапов (1–8) прошла до того, как это выяснилось. Все они оказались **независимыми
срезами от дефолтной точки**, а не накопительной оптимизацией: каждый этап перебирал свои
параметры, а все остальные молча стояли на дефолтах.

Контрольный прогон собранного из этих находок набора дал OutOfSample 326 501 — **хуже**, чем один
только `Band abs` = 4 (332 098). Классический случай: параметры, подобранные независимо, вместе
работают хуже. Этапы были переиграны накопительно.

База каждого следующего этапа — значения, найденные на предыдущих, зафиксированные через

## Проверка найденного набора в тестере

Итоговые параметры применены к роботу `KorovinPortfolio` и прогнаны в тестере на всём периоде
одним непрерывным прогоном (в отличие от оптимизатора, где обучение и проверка — два отдельных
прогона).

Условия: 04.01.2016 — 20.08.2026, депозит 2 000 000, расчёт портфеля включён, комиссия
**0,05 % выставлена на все три торговые вкладки** (скринер, GOLD, LQDT), `Reopen mode` = `On`.

| Метрика журнала тестера | Значение |
|---|---|
| Чистая прибыль | **8 950 625 (+447,5 %)** |
| Итоговый капитал | 10 950 625 |
| Сделок | 200 |
| Прибыльных / убыточных | 174 / 26 |
| Profit factor | 3,82 |
| Recovery factor | 19,18 |
| Комиссия за весь период | 61 057 (0,7 % от прибыли) |
| `max_drawdown_percent` | −10,34 % — **читать нельзя, см. ниже** |

### Просадку тестера использовать нельзя

`max_drawdown_percent` в журнале считается по кривой **реализованных сделок** и не учитывает
переоценку открытых позиций. Для ребалансировщика, который держит позиции месяцами, это
занижает просадку в разы: тестер показал −10,34 %, реальная просадка портфеля — **32,5 %**.

Правильная оценка берётся из лога робота: в каждой записи решения есть поле `Портфель`, равное
`деньги + позиции по рынку`, то есть включающее нереализованный результат.

### Сравнение с прогоном до оптимизации

Сопоставлены два прогона на одном периоде: до оптимизации (`Continuous`, все параметры
по умолчанию, комиссия не учитывалась) и после (найденный набор, комиссия 0,05 %).

| | До оптимизации | После | |
|---|---|---|---|
| Ребалансировок | 196 | **49** | в 4 раза меньше |
| — Scheduled / Deviation / LoadChange | 131 / 30 / 35 | 36 / 8 / 5 | |
| Закрытых торговых позиций | 329 | **74** | в 4,4 раза меньше |
| Доля прибыльных сделок | 69,0 % | 67,6 % | без изменений |
| Реализовано по сделкам | 6 468 787 | 6 072 103 | −6 % |
| Дивидендов получено | 2 132 198 | **2 303 998** | +8 % |
| **Средний результат сделки** | 19 662 | **82 055** | в 4,2 раза выше |
| **Прибыль на ребалансировку** | 42 390 | **183 805** | в 4,3 раза выше |
| Портфель на финише | 10 308 503 | **11 006 431** | +6,8 % |
| **Просадка портфеля (из лога)** | 34,6 % | **32,5 %** | −2 п.п. |
| Момент просадки | 30.09.2022 | 26.09.2022 | тот же обвал |

Прогон «после» шёл **с комиссией 0,05 %**, прогон «до» — без комиссии вовсе. То есть при худших
условиях исполнения результат оказался лучше.

### Что на самом деле дала оптимизация

Не рост доходности и не снижение риска, а **эффективность сделки**. Робот делает вчетверо меньше
движений, но каждое несёт вчетверо больше результата; попутно вырос дивидендный доход, потому что
позиции держатся дольше и реже переоткрываются.

Просадка осталась практически прежней — и это ожидаемо. Она определяется аллокацией (50 % акций)
и глубиной обвала 2022 года, а не параметрами лестницы: обе просадки пришлись на один и тот же
момент, конец сентября 2022. Чтобы её снизить, нужно менять долю акций, а она зафиксирована
решением, а не подбором.

### Оговорка к методу подсчёта просадки

Просадка считается по точкам ребалансировок из лога — это оценка **снизу**: между записями
портфель мог проседать глубже. У прогона «после» таких точек 49 против 196, поэтому его оценка
грубее, и реальная разница может отличаться в обе стороны. Для точного сравнения нужна дневная
кривая капитала, которой в логе нет.

## Ограничения этих результатов

* **Проверочный период медвежий.** С 2025 по август 2026 рынок падал, золото росло. Всё, что
  снижает долю акций или частоту сделок, на нём выигрывает. На растущем рынке выводы могут быть
  иными — особенно про широкую полосу.
* **Аллокация не оптимизировалась** (см. этап 1): по критерию OoS она вырождается в «портфель =
  золото». Значения 50/25/25 заданы решением, а не подбором.
* **Просадка не контролировалась в ходе оптимизации**: метрика `max_draw_down` из отчёта
  оптимизатора неинтерпретируема, а `max_drawdown_percent` из журнала тестера считается только
  по реализованным сделкам и занижает просадку втрое. Единственная надёжная оценка — поле
  `Портфель` из лога робота. По ней просадка итогового набора 32,5 % против 34,6 % до
  оптимизации, то есть риск практически не изменился.
* **Один период проверки.** Полтора года — короткий отрезок; устойчивость выводов проверялась
  только требованием плато, а не вторым независимым периодом.

### Главное содержательное отличие от первой серии

Направление настройки поменялось на противоположное. На прежнем составе выигрывал **поздний**

составе лучше работает **ранняя и частая** докупка: полоса вдвое уже, докупка начинается
с просадки 3 % вместо 8 %, резерв полностью расходуется уже к 35 % вместо 55 %, кривая
линейная вместо выпуклой.

дивидендные истории второго эшелона (MRKC, MRKP, MSRS, LSNGP, PMSBP). Они колеблются чаще
и глубже, и стратегии выгодно ловить эти колебания, а не ждать редких обвалов рынка.

Отсюда практический вывод: **параметры лестницы привязаны к составу портфеля**. Менять список
бумаг без переоптимизации нельзя — прежний набор на новом составе теряет 37 % результата.

### Ещё одна особенность API, всплывшая в этой серии

Значение выключенного (`on: false`) числового параметра берётся не из заводского дефолта,
а из того, что сохранено в настройках робота оптимизатора. В этой серии `Euphoria weight`
всё время шёл со значением 0 (осталось от первой серии), а на этапе 7 он был по ошибке
зафиксирован как 0,3 — «текущее» значение из `params_get`. Результат сразу упал с 20,74
до 19,61 млн.

**Проверять фактические значения нужно в отчёте о прогоне** (`optimizer_get_report` содержит
полный набор параметров каждого прогона), а не в `optimizer_params_get`.

Второе наблюдение: **текущую точку надо включать в сетку перебора**. На этапах 4, 5 и 7 все
перебранные комбинации оказались хуже уже установленных значений просто потому, что сами эти
значения в сетку не попали.

а `Band abs` 2 % от капитала при тринадцати бумагах перекрывает `Band rel` 20 % от целевой
позиции. Различия появляются только при `Band abs` ≤ 1,5 и высокой доле акций, когда цель
на бумагу вырастает настолько, что относительная полоса выходит вперёд.

То есть подбирать `Band rel` имеет смысл только в паре с узкой абсолютной полосой.

## Починка дневного ряда и переподбор полос

### Ряд смешивал сессии — все прежние цифры получены на нём

Торговое окно отсекало бары как точку запуска, но `KorovinDailySeries.Update` строил ряд
из всех свечей подряд. Закрытием дня становилась последняя свеча суток — вечерняя сессия акций
23:00, тогда как золото закрывается в 18:00, а решения принимаются до 19:00. Выходные дни
попадали в ряд целиком, несмотря на выключенные субботу и воскресенье.

Последствия системные, потому что ряд — это ещё и шкала времени:

* `Long sma period` = 200 и `Speed window` = 5 отсчитываются в элементах ряда, где с 2024 года
  бывало до 7 записей в неделю вместо 5 — SMA покрывала около 143 торговых дней вместо 200;
* `decayDaily = Peak decay / 252` предполагает 252 записи в год, при выходных в ряду затухание
  пика ускорялось примерно до 19-20 % годовых вместо 15 %;
* `Exit delay days` и `Stale days` сжимались в календарном выражении.

Исправлено передачей предиката торгового времени в `Update`: свечи вне окна пропускаются
и при поиске закрытия дня, и при определении текущей цены.

| | ряд не фильтрован | ряд отфильтрован |
|---|---|---|
| Портфель | 18 671 604 | **18 244 676** |
| Просадка | 19,7 % | 21,3 % |
| Ребалансировок | 211 | 233 |
| Сделок | 679 | 718 |

Рост активности закономерен: ряд стал короче, окна метрик покрывают больше календарного
времени, затухание пика замедлилось до заявленного.

### Оптимизатор после исправления синхронности табов

Под оптимизатором логика запускалась по первому же обновившемуся табу скринера, поэтому
портфель считался по смеси: одна бумага по новой свече, остальные по предыдущей. Добавлена
проверка `AllStockTabsSynchronized` — запуск только когда у всех табов совпало время последней

## Расписание: плановая ребалансировка почти не нужна

`Schedule` = `Interval`, перебор `Interval days` от 5 до 60 шагом 5.

Зависимость односторонняя: **чем реже плановая, тем лучше**. Значения 50, 55 и 60 дают
идентичный результат — при таком интервале плановая практически перестаёт срабатывать,
и портфель ведут только лестница и отклонения весов.

| Конфигурация | Портфель | Просадка | Сделок | Прибыль на 1 % просадки |
|---|---|---|---|---|
| `Weekly` / день 1 | 20 494 350 | 20,3 % | 590 | 910 тыс. |

**+5,7 % прибыли при той же просадке.** Выбрано `Schedule` = `Interval`, `Interval days` = 50
(центр плато 45–60).

### Что это означает содержательно

Плановая ребалансировка по календарю на этом портфеле **вредна**. Полезную работу делают
два повода: `LoadChange` (движение лестницы) и `Deviation` (выход веса за полосу) — оба
привязаны к состоянию рынка, а не к дате. Календарная плановая добавляла сделки в моменты,
когда рынок этого не требовал, и платила за них комиссией.

В структуре поводов после смены: `LoadChange` 92, `Deviation` 52, `Scheduled` 27 — против
`LoadChange` 103, `Deviation` 28, `Scheduled` 30 при недельном расписании. Отклонения весов
стали ловиться вдвое чаще, потому что их больше не «съедала» подоспевшая плановая.

Интервал в 50 дней здесь работает не как расписание, а как страховка: если рынок стоит
и ни один рыночный повод не срабатывает, портфель всё равно проверяется раз в квартал.
